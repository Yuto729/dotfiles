# Invariants検証の観点（7つ）

システムが常に守るべき不変条件。これらが破られると、データの整合性やセキュリティが損なわれる。

## チェックリスト

```
□ マルチテナント境界
  organization_id/tenant_idのフィルタは全クエリにあるか？
  他のテナントのデータが漏れる可能性はないか？

□ 認可
  このリソースに対する操作権限チェックはあるか？
  オブジェクトレベルの権限確認は実装されているか？

□ 一意性
  重複してはいけないデータの制約は？
  DB制約（UNIQUE）かアプリケーション層のどちらで保証するか？

□ 整合性
  関連データ（FK先）が削除されても破綻しないか？
  CASCADE DELETE か保護（PROTECT）か、どちらが適切か？

□ 冪等性
  同じ操作を2回実行しても安全か？
  リトライ時に重複作成や二重課金が発生しないか？

□ 時間軸
  作成日時 < 更新日時 の制約は守られるか？
  タイムスタンプの逆転や未来日時の設定は防げるか？

□ ステートマシン
  禁止された状態遷移（例: 出荷済→未発送）はブロックされるか？
  全ての状態遷移パスは定義されているか？
```

## 実践

- 実装前に、この変更で影響を受けるinvariantsをリストアップ
- AIに質問: 「この変更で壊れうるinvariantsは？」
- コードレビュー時に、invariantsが保たれているか確認

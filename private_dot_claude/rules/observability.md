# Observability観点（3つ）

システムの状態を外部から観測できるようにする。観測できないものは、改善できない。

## チェックリスト

```
□ ログ
  エラー時に原因特定できる情報は記録されるか？
    - correlation_id（リクエストを横断追跡）
    - 入力値（個人情報をマスクした上で）
    - エラーメッセージとスタックトレース
  構造化ログ（JSON形式）になっているか？
  ログレベル（DEBUG/INFO/WARN/ERROR）は適切か？

□ メトリクス
  この機能の健全性を示す数値は取れるか？
    - 成功率（success rate）
    - レイテンシ（p50/p95/p99）
    - スループット（requests per second）
    - エラー率（error rate）
  ビジネスメトリクス（注文数、売上など）も記録されているか？
  メトリクスの保存先（Prometheus/CloudWatch等）は決まっているか？

□ アラート
  壊れたら気づけるか？
  何を閾値にするか？
    - エラー率が5%を超えたら
    - レイテンシp95が3秒を超えたら
    - ジョブキューの遅延が10分を超えたら
  誰が通知を受け取るか？
  Runbook（対応手順）は用意されているか？
```

## 実践

- 新機能を書く前に、既存の類似機能がどこを観測しているかgrepで確認
- 各PRで最低1つ、ログかメトリクスを追加
- 障害発生時に「どうすれば早く気づけたか？」を振り返り、観測ポイントを追加

# 失敗モード発見の観点（6つ）

実装時に想定すべき失敗シナリオ。これらを考慮しないと、本番環境で予期しない障害が発生する。

## チェックリスト

```
□ Timeout
  外部API/DB呼び出しにタイムアウト設定はあるか？
  タイムアウト値は適切か？（短すぎ/長すぎないか）

□ Retry
  リトライは冪等か？（同じリクエストを複数回送っても安全か）
  リトライ上限回数は設定されているか？
  指数バックオフ（exponential backoff）は実装されているか？

□ Partial Failure
  処理の途中で失敗した場合、不整合は起きないか？
  トランザクション境界は適切か？
  補償トランザクション（Saga pattern）は必要か？

□ Race Condition
  同時実行で壊れないか？
  SELECT → UPDATE の間に別トランザクションが割り込む可能性は？
  楽観的ロック（version）か悲観的ロック（SELECT FOR UPDATE）か？

□ Null/Empty
  null、空文字、空配列のケースは考慮されているか？
  Optional型やNullableアノテーションは適切か？
  デフォルト値は妥当か？

□ Boundary
  0件、1件、上限ギリギリ、上限超過のケースは考慮されているか？
  ページネーションは実装されているか？
  バッチ処理のチャンクサイズは適切か？
```

## 実践

- 各機能で最低1つの異常系テストを書く
- AIに質問: 「この実装で想定すべき失敗モードは？」
- デプロイ前に、失敗時の挙動を確認（カオスエンジニアリング）
